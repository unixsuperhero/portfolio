◆ Here's how I'd structure it, shaped around your approach — the through-line of
  the whole series is killing procedural thinking and replacing it with modeling
  things:

  Phase 1 — Think in data, not steps

  1. Procedural thinking and what it costs you — the 20 problems, and why they
     all have one root cause.
  2. Find the thing — every program is about some meaningful thing; name it and
     its information before writing any procedure.
  3. Objects answer questions — one instance, many answers. Initialize once, ask
     many things.
  4. Name the answer, not the computation — query methods named after the value
     returned, and only doing what the name suggests.
  5. The busy service object teardown — your refactor video: one procedure in, a
     modeled thing out, 20 problems gone.

  Phase 2 — Build real models

  6. Constructor context is part of the object — keep related information
     together so debugging never means walking backward through code.
  7. Private methods are a smell — they trap useful answers inside a procedure;
     find the missing concept instead.
  8. Model the whole system, not one form — surrounding things, collections,
     relationships, histories.
  9. Derived answers are still data — combining info without mutating state is
     modeling, not procedure.
  10. Separate mechanism from business specifics — the form engine vs.
      SSO/POSOI-style details; variation through definitions, not branches in
      the mechanism.

  Phase 3 — Compose like an engineer

  11. Vertical composition — lower-level capabilities composing into
      higher-level concepts.
  12. Horizontal reuse — the same concept answering different callers' different
      questions (this is what makes an object useful vs. a one-call-site
      service).
  13. Atomic capabilities, unrestricted composition — expose the intermediate (
      sum, not just squared_sum); never import the current caller's assumptions
      into a lower level.
  14. Query-order independence — callers ask in whatever order they need, no
      preparatory call sequences.
  15. Self-service UIs — expose intermediate capabilities through the interface
      so users compose without a developer changing code per use.

  Phase 4 — Operate like a senior

  16. Onboard anyone in under a second without showing code — your full-app
      organization video; the system map is the documentation.
  17. Change-frequency design — business rules churn, mechanics don't; put the
      churn where it's data, not procedure rewrites.
  18. Debugging as a modeling diagnostic — every painful debug session points at
      fragmented information; read it that way.
  19. Review code for the mentality, not the style — what to actually look for
      in a PR: verbs-as-subjects, single-use services, trapped answers.
  20. When to break your own rules — genuinely unsettled distinctions,
      performance realities, and knowing the difference between a principle and
      a ban.

  The arc: phases 1–2 make someone who writes good classes, phase 3 makes them
  dangerous, phase 4 makes them senior — someone whose systems absorb change
q  refactor works instead of just watching problems vanish.
